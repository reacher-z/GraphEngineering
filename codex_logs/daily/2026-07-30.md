#### Root cause: a genuine cross-language divergence, not a harness artifact

The campaign harness is deterministic in itself — the fault matrix is a pure
nested loop over closed tuples whose SHA-256 is asserted against the fixture
before the run — and the failing entry varies run to run, which is the signature
of a wall-clock race rather than of ordering or state bleed.

The per-attempt `timeoutMs` is the one bound in the entire cycle contract that
is not driven by the injected trusted clock. `deadlineAt`, `durationMs` and
`maxDurationMs` all use the frozen clock and are deterministic; attempt timeout
is measured against real time. The two runtimes then disagree about whether it
can fire at all for a synchronous handler:

- TypeScript races a `setTimeout` macrotask against a handler invoked through
  `Promise.resolve().then(...)`. A synchronous handler settles in a microtask,
  and the timer cannot run until the microtask queue drains, so a synchronous
  TypeScript handler **can never time out** at any load. Measured: 0 timeouts in
  20 iterations with a handler blocking the loop for 300 ms against
  `timeoutMs: 100`.
- Python dispatches a non-coroutine handler through `asyncio.to_thread`, so it
  must cross the thread pool and re-acquire the GIL. That genuinely races the
  wall clock. Measured: dispatch latency for the same handlers inflated from a
  p99 of 0.86 ms to a 661 ms maximum under 32 CPU spinners, past the 100 ms
  bound.

When Python times out, the attempt fails before the event carrying the campaign
boundary is ever constructed, so the fault hook never fires and the harness
reports "did not fire". The consequence is durable rather than cosmetic: the
patch-planner binding is `idempotent`, so a load-induced timeout writes an
in-doubt activity into the event stream. Two conforming runtimes can therefore
produce different durable histories for identical inputs purely because of
machine load.

Reproduction was confirmed rather than inferred: forcing the planner binding to
`timeoutMs: 1` with a 50 ms handler reproduces the reported error text verbatim,
and an unmodified tree under 32 spinners failed 4 of 5 runs.

#### Fix applied and what remains open

The harness change is minimal and normative-preserving: every conformance
campaign handler is now a coroutine function, so dispatch completes in its first
event-loop step and the timer can never preempt it — exactly TypeScript's
dispatch shape. Three files under `tools/conformance/` changed; no runtime and
no normative behavior. No retries were added, per plan §23.9.

Verification: visibility and checkpoint campaigns each 10/10 idle and 3/3 under
32 spinners, against an unmodified-tree control of 1/5; instrumented dispatch
under load went from 1 timeout and a 661 ms maximum to 0 timeouts and a 24 ms
maximum; and the Python report bytes are unchanged (1,948,938 and 391,073
bytes), which matters because `run.mjs` asserts `deepEqual` between the Python

`node tools/conformance/run.mjs` now exits 0, including 35 exact PatchAccepted
visibility fault recoveries and 15 exact checkpoint fault recoveries. The gate
that opened this session red is green.

The underlying runtime divergence is **not** fixed and is registered as
`D8-CYCLE-TIMEOUT-DIVERGENCE-090`. `spec/cycle-semantics.md` now records it
normatively, bars synchronous handlers from cross-language campaigns, requires a
deliberate awaited block for any campaign that means to exercise attempt

running Python's non-coroutine handlers inline would match TypeScript but retire
a strictly stronger guarantee Python has and tests — a blocking synchronous
handler being timed out, charged, and never committed — which TypeScript cannot
express at all; driving attempt timeout from the injected clock would make the
controller fully deterministic but would make `timeoutMs` unreachable in the
campaigns that require it to fire.

### The safety fact this contract exists for

`packages/runtime/src/scheduler.ts:982` classifies a `barrier` node together
with `transform` and executes it as an ordinary deterministic node. A graph that
declares a threshold, quorum or deadline policy in a `barrier` node's `config`
therefore has that policy ignored entirely — an unsatisfied barrier passes
silently. That is a wrong answer, not a missing feature.

The contract makes a pre-dispatch capability rejection of a policy-bearing
barrier the first required deliverable, ahead of any barrier functionality,
reusing the accepted foreign-condition preflight mechanism. `docs/CONCEPTS.md`
and `docs/FAILURE_MODES.md` were corrected to state this limit explicitly and to
tell users not to encode real thresholds in `barrier` nodes today.

1. **`votes` cardinality was unsatisfiable.** The contract required exactly one

3. **`GE1422` to `GE1424` suppression was unspecified.** The chain is now

4. **Confidence asymmetry was undocumented.** A vote is optional `1..10000`

   published surface.
5. **The decision schemas accepted node IDs the compiler cannot produce.** Both

   Graph IR node-ID pattern, and `route-decision.schema.json` carries a separate
